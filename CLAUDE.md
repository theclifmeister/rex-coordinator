# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin (`.claude-plugin/plugin.json`) that turns one Rex terminal pane into a **coordinator**: it never does the work itself, but hands each task to a fresh worker Claude in its own Rex tab and git worktree, then merges the result into a feature branch. Everything is bash + markdown; there is no build step and no test suite. Runtime deps: `rex`, `git`, `jq`, `bash`, `tsk` ≥ 0.14.1.

## Checking changes

CI (`.github/workflows/ci.yml`, on PRs, pushes to `main`, and called by `release.yml`) runs these; run them locally before pushing:

- Lint: `cd scripts && shellcheck -x ./*.sh ../hooks-handlers/session-start.sh ../tools/*.sh` (scripts source `lib.sh`; `-x` from `scripts/` follows it). Must be clean, not just warning-free.
- Validate JSON: `jq empty .claude-plugin/plugin.json .claude-plugin/marketplace.json hooks/hooks.json`.
- Manifests agree: the marketplace's single entry has the same `name` as `plugin.json`, `source: "./"`, and **no `version`** (`plugin.json` alone carries it, as `x.y.z`).
- `claude plugin validate .` — non-strict on purpose: `--strict` fails because `CLAUDE.md` sits at the plugin root (the repo ships whole, `source: "./"`) and is "not loaded as project context". The icon line is directory-submission advice and doesn't affect the result. Works without login.
- CI **fails** when `skills/`, `scripts/`, `hooks/`, `hooks-handlers/` or `plugin.json` changed since the last `v*` tag (or the PR base) without a version bump: users would not get that change. It skips when there is no tag/base. So a PR to `main` that changes the plugin must carry the bump, which is what the release branch does (below). CI installs `@anthropic-ai/claude-code@latest` for the validate step; never run that `npm install -g` locally.
- Real testing means running `/coordinator-start` in a Rex pane of some scratch git repo, in a session started with `claude --plugin-dir <checkout>` (or with the release installed). Most scripts refuse to run outside the coordinator pane (`require_coordinator`).

## Releasing

This repo is also the `theclifmeister` marketplace (`.claude-plugin/marketplace.json`, one entry, `source: "./"`); users install `rex-coordinator@theclifmeister`. Claude Code ships an update only when the `plugin.json` `version` changes on `main`.

`main` on GitHub only takes pull requests ("Changes must be made through a pull request"); a direct push is rejected. A release goes:

1. With the work merged into local `main` and the tree clean, run `tools/bump-version.sh patch` (`minor`/`major` only when the user says so). It refuses a dirty tree, a branch other than `main`, a bad argument, or an existing `release/vX.Y.Z` branch (local or `origin/`) or `vX.Y.Z` tag. It creates branch `release/vX.Y.Z` with one commit `Release vX.Y.Z` (only `plugin.json`) on top of `main`, without switching: the checkout stays on a clean `main`. It prints the next steps and does not push, open the PR or tag.
2. `git push origin release/vX.Y.Z`.
3. Open the PR, wait for CI, merge it with a merge commit. `gh` must act as the repo owner account without switching the user's active `gh` account: prefix each call with the owner's token, e.g. `GH_TOKEN=$(gh auth token --user theclifmeister) gh pr create -R theclifmeister/rex-coordinator --base main --head release/vX.Y.Z --title "Release vX.Y.Z" --fill`, then `... gh pr checks -R theclifmeister/rex-coordinator release/vX.Y.Z --watch`, then `... gh pr merge -R theclifmeister/rex-coordinator release/vX.Y.Z --merge --delete-branch`.
4. `git pull --ff-only origin main` (local `main` is an ancestor of the PR merge, so this fast-forwards).

On the merge, `.github/workflows/release.yml` runs CI, then creates tag `vX.Y.Z` and a GitHub Release if that tag doesn't exist yet. The notes list every merge commit since the previous `v*` tag, newest first: the PR merge and the coordinator's `Merge <slug>: ...` task merges inside it (`--first-parent` would hide those), never `Release v...` commits; without merges, the plain commits. It uses `GITHUB_TOKEN` only and never commits. `workflow_dispatch` reruns it; it refuses a commit that isn't on `main`.

- Never make or push `v*` tags by hand, and never put `version` on the marketplace entry.
- Everything committed ships in users' plugin cache, so keep repo-only files (`tools/`, `.github/`) small.

Dev setup: the marketplace install (auto-update on) runs in every repo, this one too, so merging into `main` changes nothing live until a release ships. To try unreleased changes, start a separate session with `claude --plugin-dir <checkout>` (or `CLAUDE_CODE_PLUGIN_DIRS=<checkout>`): that copy (`rex-coordinator@inline`) takes precedence over the installed one for that session only, including its `SessionStart` hook. Workers launched from it run plain `claude` and get the installed plugin; it's not clear whether an exported `CLAUDE_CODE_PLUGIN_DIRS` reaches them (`rex run` uses the login-shell environment), and that doesn't matter because workers don't use the plugin's scripts. A `~/.claude/skills/rex-coordinator` symlink is obsolete: an installed plugin with the same name blocks it even when disabled, so the old disable/enable toggle left nothing loaded; `rm` the link. When testing plugin commands in a throwaway `HOME`, never use local or project scope: those write `.claude/settings*.json` in the repo (the main checkout, even from a worktree), not under `HOME`. Don't enable the plugin at local scope as well: Claude Code resolves local scope to the main checkout's `.claude/settings.local.json` from every worktree, and with the plugin enabled there each session in a worktree (nested in `.claude/worktrees/` or not) adds a `local` record with that `projectPath` to `installed_plugins.json`. The records outlive the worktree, and a bare `claude plugin update` can hit a stale one. Without the local enable no record appears, and the user-scope install still loads (both verified with `claude -p` and an isolated HOME). `claude plugin uninstall <id> --scope local --keep-data`, run from a path, removes only that path's record, but it also deletes the plugin's key from the shared `settings.local.json`. That's why `plugin_drop_local_record` (`lib.sh`) saves that file first and puts it back. A missing path is created empty for the call and then removed. `finish-task.sh` runs it for the closed worktree. It's best-effort and silent, and skipped without `claude`. `plugin-records.sh [--fix]` handles the old ones: gone paths under `.claude/worktrees/`, or ones in this repo that belong to no open task. `doctor.sh` notes a local enable.

## How the pieces fit

- **Activation** — `/coordinator-start` (`skills/coordinator-start/`) runs `scripts/start.sh`, which first runs `scripts/doctor.sh --quiet` (required `rex`, `git` ≥ 2.31, `jq`, bash, `tsk` ≥ 0.14.1 — `scripts/tsk-version.sh`, shared with `session-start.sh`; an unparsable tsk version and a missing `tsk-cli` skill in `${CLAUDE_CONFIG_DIR:-~/.claude}/skills` are only notes; the check needs no jq) and refuses if it fails, then writes `block=`, `session=`, `feature=` to `<git-common-dir>/rex-coordinator/state`. With a branch argument it first checks that branch out in the main checkout, refusing a dirty checkout or a merge/rebase in progress. The **feature branch is the main checkout's current branch** (`feature_branch`/`resolve_feature` in `lib.sh`); `feature=` is only the last one seen (fallback, with a warning, when the checkout is detached or mid-rebase). When the coordinator's scripts see a new branch they update `feature=` once, after pinning open tasks without a `.base` to the old value; `status.sh` and `session-start.sh` report the switch ("feature branch changed from X to Y" plus tasks still based on X). `session-start.sh` only reads. On every session start / `/clear` / compaction, `hooks/hooks.json` runs `hooks-handlers/session-start.sh`, which emits `additionalContext` telling Claude to load the `rex-coordinator:coordinator` skill — but only when `$REX_BLOCK` matches the recorded block and `CLAUDE_ROLE` is not `worker`. Every other pane stays silent; keep it that way. In the coordinator pane only, it prepends a warning if `rex` or `jq` is missing or tsk is missing or older than 0.14.1 (one `tsk --version` call), and without jq prints the context as plain text instead of JSON.
- **Playbook** — `skills/coordinator/SKILL.md` is the coordinator's behavior spec (what to run, how to merge, rules). Changes to the flow usually mean editing this file, and keeping it consistent with the scripts it names.
- **Task lifecycle** — `new-task.sh <slug>` (branch + worktree at `.claude/worktrees/<slug>` off the feature branch, recorded as the task's base in `tasks/<slug>.base`, brief rendered from `skills/coordinator/brief-template.md` via `sed` placeholder substitution) → coordinator fills `{{TODO}}`s → `launch-worker.sh` (refuses while `{{TODO` remains; `rex run ... env CLAUDE_ROLE=worker claude`, stores block ID in `tasks/<slug>.block`) → worker writes `reports/<slug>-report.md` and `rex send`s `REPORT DONE|BLOCKED <slug>` → coordinator merges `--no-ff` → `finish-task.sh` (refuses unless merged into the task's base — `task_base`: `.base`, else `feature=` for older tasks — unless `--abandon`; ledger and board text name that base; removes `.base` and Claude Code's local plugin record for the worktree, see Dev setup).
- **Side channels** — `research.sh <topic> [--ref <branch|commit>]` opens a read-only worker in its own background tab, in a detached worktree at `.claude/worktrees/_research/<topic>` checked out at the feature branch tip or `--ref` (never the main checkout's working tree; `_` can't start a slug, so no clash with task worktrees). `tasks/research-<topic>.block` holds the tab, `tasks/research-<topic>.ref` holds `<ref> <short sha>` (a commit `--ref` is stored as its short sha; `research_reads` in `lib.sh` renders it as `<branch>@<sha>` or just `<sha>`, for status and the ledger), answer in `research/<topic>.md`, no branch; `finish-task.sh` force-removes the worktree and the ref file. `tell.sh` sends long messages via a file in `messages/` plus one short typed line, because long `rex send` input gets truncated. `watch.sh` is a background fallback that detects a report file (or, for research, a non-empty answer file), a `REPORT DONE|BLOCKED <slug>` marker at the start of a line in a task tab (after optional spaces and Claude Code's `⏺`, so a brief on screen can't trigger it), or a dead tab. It never scans a research tab's text: the typed instruction already contains `RESEARCH DONE <topic>`.
- **Board (tsk ≥ 0.14.1, required at activation; every call still tolerates it missing)** — `new-task.sh <slug> [T<n>] [--title ...]` links (or creates — then `--title` is required, checked before any branch exists) a tsk task and writes `tasks/<slug>.tsk` (`<uuid> T<n>`); its title/notes/steps go into the brief by `jq`/`awk`, never `sed` (notes hold `|&/` and newlines). `launch-worker.sh` → `started --no-dispatch` + one guarded notes line; `finish-task.sh` merged → `review --on you` and the link moves to `review/<slug>.tsk` (only if the task really is in review); `--abandon` → note + `done`, link removed. `board.sh` does blocked/unblock/show by slug. `watch.sh` also exits on `BOARD REPLY`; `board-watch.sh` polls `review/*.tsk` (45 s) for `BOARD SENT BACK|DONE|MOVED`, records `seen=` in the link so each event fires once, and drops the link on done. `new-task.sh` linking a task again removes its `review/` link. Thread = the task's base branch made a thread name (`thread_name`: letters, digits, `-`, `.`): `tsk add --thread` on create (retried without it if refused), `tsk_set_thread` on link only when the task has none (`edit --thread`, tsk ≥ 0.14.1; exit 2 just warns). `status.sh` shows `steps d/t` (0.14 rows carry `steps_done`/`steps_total`; else counted from `.steps`). `recall.sh --board` does one `tsk list <uuid> --json` per task of the project (live, `--done`, `--archived`).
- **Memory** — `finish-task.sh` appends one line per closed task to `history.md` (date, slug, merged/abandoned/research, sha (research: `<branch>@<sha>` or `<sha>`), board T-number if linked, the report's `Summary:` line, paths relative to the state dir — older lines hold absolute paths, and both must keep working); `session-start.sh` puts the last 15 lines in the coordinator's context and names the state dir; `scripts/recall.sh [--board] <word>...` searches the ledger, briefs, reports and research answers (and, with `--board`, the repo's board tasks).
- **Shared helpers** — `scripts/lib.sh` (`set -euo pipefail`, `die`, `state_dir`, `state_get`, `repo_root`, `require_coordinator`, `check_slug`, `state_set`; feature: `checkout_branch`, `resolve_feature`, `feature_branch`, `task_base`, `open_task_slugs`, `tasks_based_on`; board: `have_tsk`, `tsk_try` (warns, never fails; exit in `$TSK_RC`, exit 3 = indeterminate), `tsk_task`, `thread_name`, `tsk_set_thread`, `tsk_link`, `tsk_link_file`, `one_line`, `canon_dir`; `research_reads`; plugin records: `plugin_records_file`, `plugin_local_records`, `plugin_drop_local_record`). `repo_root` is derived from the git common dir so scripts work from inside a worktree too.

## Conventions and invariants

- State lives only in `<git-common-dir>/rex-coordinator/` (never committed, shared across worktrees); `start.sh` adds `.claude/worktrees/` to `.git/info/exclude` rather than `.gitignore`.
- `CLAUDE_ROLE=worker` is the guard that stops workers from coordinating; every entry point checks it.
- Board writes: only the coordinator (its scripts, or commands named in the playbook) changes a board task's status, notes, base or replies. Workers may only `tsk steps <uuid> add|toggle` on their own task (the brief says so). Every board call is best-effort (`tsk_try`) and skipped without `tsk`; a tsk failure never fails git/Rex work. Always `-p "$root"` (absolute) on project-scoped calls and address tasks by UUID — a worktree is a different tsk project. Always `started --no-dispatch`. `done` is set only by `finish-task.sh --abandon`. Guard non-idempotent writes (`--append-notes`, `reply`, `steps toggle`) by reading first.
- Never test against the real board: tsk has one global store (`~/.tsk/tsk.json`); run tests through a wrapper that sets `HOME` to a throwaway dir.
- The message protocol strings (`REPORT DONE`, `REPORT BLOCKED`, `RESEARCH DONE`, `ACK <slug>-<n>`, `BOARD REPLY|SENT BACK|DONE|MOVED|IDLE`, and the report's first line `Summary: <one line>`) are matched across the brief template, `research.sh`, `tell.sh`, `watch.sh`, `finish-task.sh` and the playbook — change them everywhere at once.
- Brief template placeholders (`{{SLUG}}`, `{{WORKTREE}}`, `{{FEATURE}}`, `{{COORDINATOR_BLOCK}}`, `{{REPORT}}`, `{{TSK_NUM}}`, `{{TSK_ID}}`, `{{BOARD_TASK}}`) are filled by `new-task.sh`; lines between `<!-- board -->` and `<!-- /board -->` are dropped when no board task is linked; `{{TODO...}}` is left for the coordinator.
- Slugs must match `^[a-z0-9][a-z0-9._-]*$` (they become branch names and file names). Task slugs may not start with `research-`: `tasks/research-<topic>.*` belongs to research.
- Skills reference scripts via `${CLAUDE_PLUGIN_ROOT}`.
