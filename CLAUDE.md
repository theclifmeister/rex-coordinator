# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Claude Code plugin (`.claude-plugin/plugin.json`) that turns one Rex terminal pane into a **coordinator**: it never does the work itself, but hands each task to a fresh worker Claude in its own Rex tab and git worktree, then merges the result into a feature branch. Everything is bash + markdown; there is no build step and no test suite. Runtime deps: `rex`, `git`, `jq`, `bash`, `tsk` ≥ 0.14.1.

## Checking changes

CI (`.github/workflows/ci.yml`, on PRs, pushes to `main`, and called by `release.yml`) runs these; run them locally before pushing:

- Lint: `cd scripts && shellcheck -x ./*.sh ../hooks-handlers/session-start.sh ../tools/*.sh` (scripts source `lib.sh`; `-x` from `scripts/` follows it). Must be clean, not just warning-free.
- Validate JSON: `jq empty .claude-plugin/plugin.json .claude-plugin/marketplace.json hooks/hooks.json`.
- Manifests agree: the marketplace's single entry has the same `name` as `plugin.json`, `source: "./"`, and **no `version`** (`plugin.json` alone carries it, as `x.y.z`).
- `claude plugin validate .` — non-strict on purpose: `--strict` fails because `CLAUDE.md` sits at the plugin root (the repo ships whole, `source: "./"`) and is "not loaded as project context". The icon line is directory-submission advice and doesn't affect the result. Works without login.
- CI **fails** when `skills/`, `scripts/`, `hooks/`, `hooks-handlers/` or `plugin.json` changed since the last `v*` tag (or the PR base) without a version bump: users would not get that change. It skips when there is no tag/base. So a PR to `main` that changes the plugin must carry the bump, which is what the release branch does (below). CI installs `@anthropic-ai/claude-code@latest` for the validate step; never run that `npm install -g` locally.
- Real testing means running `/coordinator-start` in a Rex pane of some scratch git repo, in a session started with `claude --plugin-dir <checkout>` (or with the release installed). Most scripts refuse to run outside the coordinator pane (`require_coordinator`).

## Releasing

This repo is also the `theclifmeister` marketplace (`.claude-plugin/marketplace.json`, one entry, `source: "./"`); users install `rex-coordinator@theclifmeister`. Claude Code ships an update only when the `plugin.json` `version` changes on `main`.

`main` on GitHub only takes pull requests ("Changes must be made through a pull request"); a direct push is rejected. A release goes:

1. With the work merged into local `main` and the tree clean, run `tools/bump-version.sh patch` (`minor`/`major` only when the user says so). It refuses a dirty tree, a branch other than `main`, a bad argument, or an existing `release/vX.Y.Z` branch (local or `origin/`) or `vX.Y.Z` tag. It creates branch `release/vX.Y.Z` with one commit `Release vX.Y.Z` (only `plugin.json`) on top of `main`, without switching: the checkout stays on a clean `main`. It prints the next steps and does not push, open the PR or tag.
2. `git push origin release/vX.Y.Z`.
3. Open the PR, wait for CI, merge it with a merge commit. `gh` must act as the repo owner account without switching the user's active `gh` account: prefix each call with the owner's token, e.g. `GH_TOKEN=$(gh auth token --user theclifmeister) gh pr create -R theclifmeister/rex-coordinator --base main --head release/vX.Y.Z --title "Release vX.Y.Z" --fill`, then `... gh pr checks -R theclifmeister/rex-coordinator release/vX.Y.Z --watch`, then `... gh pr merge -R theclifmeister/rex-coordinator release/vX.Y.Z --merge --delete-branch`.
4. `git pull --ff-only origin main` (local `main` is an ancestor of the PR merge, so this fast-forwards).

On the merge, `.github/workflows/release.yml` runs CI, then creates tag `vX.Y.Z` and a GitHub Release if that tag doesn't exist yet. The notes list every merge commit since the previous `v*` tag, newest first: the PR merge and the coordinator's `Merge <slug>: ...` task merges inside it (`--first-parent` would hide those), never `Release v...` commits; without merges, the plain commits. It uses `GITHUB_TOKEN` only and never commits. `workflow_dispatch` reruns it; it refuses a commit that isn't on `main`.

- Never make or push `v*` tags by hand, and never put `version` on the marketplace entry.
- Everything committed ships in users' plugin cache, so keep repo-only files (`tools/`, `.github/`) small.

Dev setup: the marketplace install (auto-update on) runs in every repo, this one too, so merging into `main` changes nothing live until a release ships. To try unreleased changes, start a separate session with `claude --plugin-dir <checkout>` (or `CLAUDE_CODE_PLUGIN_DIRS=<checkout>`): that copy (`rex-coordinator@inline`) takes precedence over the installed one for that session only, including its `SessionStart` hook. Workers launched from it run plain `claude` and get the installed plugin; it's not clear whether an exported `CLAUDE_CODE_PLUGIN_DIRS` reaches them (`rex run` uses the login-shell environment), and that doesn't matter because workers don't use the plugin's scripts. A `~/.claude/skills/rex-coordinator` symlink is obsolete: an installed plugin with the same name blocks it even when disabled, so the old disable/enable toggle left nothing loaded; `rm` the link. When testing plugin commands in a throwaway `HOME`, never use local or project scope: those write `.claude/settings*.json` in the repo (the main checkout, even from a worktree), not under `HOME`. Don't enable the plugin at local scope as well: Claude Code resolves local scope to the main checkout's `.claude/settings.local.json` from every worktree, and with the plugin enabled there each session in a worktree (nested in `.claude/worktrees/` or not) adds a `local` record with that `projectPath` to `installed_plugins.json`. The records outlive the worktree, and a bare `claude plugin update` can hit a stale one. Without the local enable no record appears, and the user-scope install still loads (both verified with `claude -p` and an isolated HOME). `claude plugin uninstall <id> --scope local --keep-data`, run from a path, removes only that path's record, but it also deletes the plugin's key from the shared `settings.local.json`. That's why `plugin_drop_local_record` (`lib.sh`) saves that file first and puts it back. A missing path is created empty for the call and then removed. `finish-task.sh` runs it for the closed worktree. It's best-effort and silent, and skipped without `claude`. `plugin-records.sh [--fix]` handles the old ones: gone paths under `.claude/worktrees/`, or ones in this repo (under a workspace coordinator: in a member repo, matched by the task's `.repo`) that belong to no open task. `doctor.sh` notes a local enable.

## How the pieces fit

- **Activation** — `/coordinator-start` (`skills/coordinator-start/`) runs `scripts/start.sh`, which first runs `scripts/doctor.sh --quiet` (required `rex`, `git` ≥ 2.31, `jq`, bash, `tsk` ≥ 0.14.1 — `scripts/tsk-version.sh`, shared with `session-start.sh`; an unparsable tsk version and a missing `tsk-cli` skill in `${CLAUDE_CONFIG_DIR:-~/.claude}/skills` are only notes; the check needs no jq) and refuses if it fails, then writes `block=`, `session=`, `feature=` to `<state dir>/state` (see Conventions). Then, best-effort (a Rex failure only warns), it renames the pane's Rex tab (window) to `coordinator` and opens the `tsk` board in a **floating pane, minimized**: `session.new_layer` (`rex api call`) in the coordinator's window, one terminal block running the absolute `tsk` path in the main checkout, label `tsk`, bounds `[0.1, 0.1, 0.8, 0.8]`, `focus: false`, then `session.set_layer_state … minimized`; focus stays on the coordinator. It records `tab_window=`, `tab_label=` (the tab's previous name), `tsk_block=` and `tsk_layer=` in `state`: a rerun reuses the board while it is a floating block in this tab, leaving it open or minimized as the user has it; otherwise it closes it (only by those IDs: the layer via `session.close_layer` while it holds just our block, else the block) and puts back the old tab's name before opening a new one. An older version's split board (no `tsk_layer=`, tiled) is closed and replaced. A Rex without `session.new_layer` gets the old split (`rex split --split=right --ratio 40 --focus=false --label tsk`) with a note. No `tsk` → a note and no pane. The user brings the board up with tsk's own `alt+t` Rex action (it focuses the first placed block labelled `tsk` in the session, and focusing a minimized floating block restores it) or by clicking its capsule in the tab's minimized-windows corner; Rex's `pane.minimize_floating` (macOS default `alt+cmd+m`) hides it again. `stop.sh` closes the recorded board and renames the tab back while it is still called `coordinator`. Rex has no command side-panel (its sidebar is the session list), hence the floating pane (`lib.sh`: `rex_block_window`, `rex_window_label`, `rex_restore_tab`, `rex_has_layers`, `rex_block_layer`, `rex_open_board`, `rex_close_board`). With a branch argument it first checks that branch out in the main checkout, refusing a dirty checkout or a merge/rebase in progress. The **feature branch is the main checkout's current branch** (`feature_branch`/`resolve_feature` in `lib.sh`); `feature=` is only the last one seen (fallback, with a warning, when the checkout is detached or mid-rebase). When the coordinator's scripts see a new branch they update `feature=` once, after pinning open tasks without a `.base` to the old value; `status.sh` and `session-start.sh` report the switch ("feature branch changed from X to Y" plus tasks still based on X). `session-start.sh` only reads. **Workspace mode**: run in a folder that is not a git repo but has git repos as direct children (`ws_repos`: depth-1 children with a `.git` dir or file, found live; plain folders and files are skipped), `start.sh` takes no branch argument and writes `block=`, `session=`, `mode=workspace`, `root=<ws>` and `feature.<repo>=<branch>` per repo to the state keyed by the workspace folder (`state_path_for_dir`), opens the tsk board (floating, minimized) in `<ws>`, and prints `<repo>: <branch> @ <sha>` per repo; a non-git folder without child repos is refused. Coexistence: it refuses a workspace start while a member repo has a single-repo coordinator whose Rex block is still open, and a single-repo start while the repo's parent folder has a live workspace coordinator (`rex_block_alive`), naming that block; a gone block only gets a note. `state_dir` resolves (1) a workspace state at or above `$PWD` whose `block=` is `$REX_BLOCK` (`ws_state_walk` in `state-path.sh`), (2) the cwd's repo's own state when it exists, (3) any workspace state above, (4) the repo's (empty) state dir; a script can pin it in `_STATE_DIR` (start/stop/status do). Per repo: `feature_branch <repo>`/`resolve_feature <repo>` track `feature.<repo>=` and report a switch once as "<repo>: feature branch changed from X to Y"; `tasks_based_on <repo> <branch>`; `open_task_slugs <repo>` and `task_root <slug>` read `tasks/<slug>.repo`. `status.sh` shows a "Repos:" block (repos on their default branch with no tasks folded into one line), each task's repo, worktrees of the repos with tasks, and the board from one `tsk list --all --json` filtered to the workspace folder and paths under it. In workspace mode every task belongs to one member repo (`--repo <name>`, `ws_check_repo`; see Workspace tasks, Side channels, Wrap-up). On every session start / `/clear` / compaction, `hooks/hooks.json` runs `hooks-handlers/session-start.sh`, which emits `additionalContext` telling Claude to load the `rex-coordinator:coordinator` skill — but only when `$REX_BLOCK` matches the recorded block and `CLAUDE_ROLE` is not `worker` (in workspace mode: a workspace state at or above `$PWD` with that block; the context names the workspace, only the repos off their default branch or with open tasks, and per-repo switch notes, and that task commands take `--repo`). Every other pane stays silent; keep it that way. In the coordinator pane only, it prepends a warning if `rex` or `jq` is missing or tsk is missing or older than 0.14.1 (one `tsk --version` call), and without jq prints the context as plain text instead of JSON.
- **Playbook** — `skills/coordinator/SKILL.md` is the coordinator's behavior spec (what to run, how to merge, rules). Changes to the flow usually mean editing this file, and keeping it consistent with the scripts it names.
- **Task lifecycle** — `new-task.sh <slug> [--repo <name>]` (branch + worktree at `.claude/worktrees/<slug>` off the feature branch, recorded as the task's base in `tasks/<slug>.base`, today's date in `tasks/<slug>.date`, brief `briefs/YYMMDD-<slug>.md` rendered from `skills/coordinator/brief-template.md` via `sed` placeholder substitution) → coordinator fills `{{TODO}}`s → `launch-worker.sh` (refuses while `{{TODO` remains; `rex run ... env CLAUDE_ROLE=worker claude`, stores block ID in `tasks/<slug>.block`, titles the tab `T<n>: <slug>` from `tasks/<slug>.tsk`, or just `<slug>` without a board task, via `rex_title_window` in `lib.sh`: a Rex window label, which Claude Code's OSC title writes don't replace; a failed rename only warns) → worker writes `reports/YYMMDD-<slug>-report.md` (the path is in its brief) and `rex send`s `REPORT DONE|BLOCKED <slug>` → coordinator merges `--no-ff` → `finish-task.sh` (adds `| base: <base>` to merged and abandoned ledger lines; refuses unless merged into the task's base — `task_base`: `.base`, else `feature=` for older tasks — unless `--abandon`; ledger and board text name that base; removes `.base`, `.date` and Claude Code's local plugin record for the worktree, see Dev setup).
- **Workspace tasks** — in workspace mode `new-task.sh` requires `--repo <name>` (refused in single mode; `ws_check_repo`: a depth-1 member repo), cuts the worktree at `<ws>/<repo>/.claude/worktrees/<slug>` off `feature_branch <repo>`, writes `tasks/<slug>.repo` next to `.base`/`.date`, refuses a slug any `tasks/<slug>.*` already uses (state files are flat: slugs are unique workspace-wide), adds `.claude/worktrees/` to that repo's `.git/info/exclude` (`ensure_excluded`) and symlinks that repo's `node_modules`. Board: `tsk add -p <ws>` with no `--base` (tsk refuses one for a non-git project) on thread `thread_name "<repo>.<feature>"`; a linked `T<n>` may belong to `<ws>` or `<ws>/<repo>`; `tsk_set_thread` gets `<repo>.<feature>`. The brief's `<!-- workspace -->` … `<!-- /workspace -->` lines (the repo, and "don't touch the workspace's other repos") are dropped in single mode. `launch-worker.sh` uses `task_root`, titles the tab `T<n>: <repo>/<slug>` (`task_label`) and its notes line says `in <repo>`. `finish-task.sh` works in `task_root` (merge check, worktree, branch, `plugin_drop_local_record`), writes `<repo>/<slug>` in the ledger's slug column (one word: the sha stays field 5), says "Merged <sha> into <repo>/<base>" on the board, and removes `.repo` last. Cross-repo work = several per-repo tasks ordered with `tsk edit <uuid> --after <uuid>`; one worker never spans repos.
- **Side channels** — `research.sh <topic> [--repo <name>] [--ref <branch|commit>]` (`--repo`: workspace mode only, and required there: the worktree is in `<ws>/<repo>`, the ref defaults to that repo's feature branch, `tasks/research-<topic>.repo` records it, the instruction names the repo) opens a read-only worker in its own background tab (titled `research: <topic>`), in a detached worktree at `.claude/worktrees/_research/<topic>` checked out at the feature branch tip or `--ref` (never the main checkout's working tree; `_` can't start a slug, so no clash with task worktrees). `tasks/research-<topic>.block` holds the tab, `tasks/research-<topic>.ref` holds `<ref> <short sha>` (a commit `--ref` is stored as its short sha; `research_reads` in `lib.sh` renders it as `<branch>@<sha>` or just `<sha>`, for status and the ledger), `tasks/research-<topic>.date` its date, answer in `research/YYMMDD-<topic>.md`, no branch; `finish-task.sh` force-removes the worktree and the ref and date files. `tell.sh` sends long messages via a file `messages/YYMMDD-<slug>-<n>.md` (today's date; `<n>` counts on past older and undated ones, so `ACK <slug>-<n>` stays unique) plus one short typed line, because long `rex send` input gets truncated. `watch.sh` is a background fallback that detects a report file (or, for research, a non-empty answer file), a `REPORT DONE|BLOCKED <slug>` marker at the start of a line in a task tab (after optional spaces and Claude Code's `⏺`, so a brief on screen can't trigger it), or a dead tab. It never scans a research tab's text: the typed instruction already contains `RESEARCH DONE <topic>`.
- **Board (tsk ≥ 0.14.1, required at activation; every call still tolerates it missing)** — `new-task.sh <slug> [T<n>] [--title ...]` links (or creates — then `--title` is required, checked before any branch exists) a tsk task and writes `tasks/<slug>.tsk` (`<uuid> T<n>`); its title/notes/steps go into the brief by `jq`/`awk`, never `sed` (notes hold `|&/` and newlines). The brief's board block has the worker plan with the task's steps: before starting, 3–7 verb-first steps when the task has none (no bookkeeping), or the user's steps as the plan (add only for missed work, never edit/remove/reorder them); tick each as it is done (read first); unticked steps go under `## Not done` in the report. The coordinator never adds steps; it sees progress as `steps d/t` in `status.sh`. `launch-worker.sh` → `started --no-dispatch` + one guarded notes line; `finish-task.sh` merged → `review --on you` mirroring the report (done = merge sha + `Summary:`; each `- PASS|FAIL|SKIP <text>` line under `## Checks` a check, left `open` with the result in the text (`PASS: `/`FAIL: `/`SKIP: `, `check_spec`): the ticks are the user's, so the plugin never sets passed/failed on its own checks; max 20 plus a "… N more" item, texts cut to 300 chars, under tsk's 4096-byte cap; then the coordinator's `--check`s; next = `## Open questions` joined, left out for `none`; one guarded `Report: <path>` notes line; no `## Checks` PASS/FAIL/SKIP lines → summary only) and the link moves to `review/<slug>.tsk` (only if the task really is in review); `--abandon` → note + `done`, link removed. `board.sh` does blocked/unblock/show/check by slug; `check` adds open prefixed checks (a same-text one is replaced, and goes back to open) and re-passes the round's existing checks with their states (the user's marks), because every `tsk status … review` call replaces the round's whole check list (states are kept by text, not for duplicate texts, so `tsk_review` re-sets them by position). `watch.sh` also exits on `BOARD REPLY`; `board-watch.sh` polls `review/*.tsk` (45 s) for `BOARD SENT BACK|DONE|MOVED`, records `seen=` in the link so each event fires once, and drops the link on done. `new-task.sh` linking a task again removes its `review/` link. Thread = the task's base branch made a thread name (`thread_name`: letters, digits, `-`, `.`): `tsk add --thread` on create (retried without it if refused), `tsk_set_thread` on link only when the task has none (`edit --thread`, tsk ≥ 0.14.1; exit 2 just warns). `status.sh` shows `steps d/t` (0.14 rows carry `steps_done`/`steps_total`; else counted from `.steps`). `recall.sh --board` does one `tsk list <uuid> --json` per task of the project (live, `--done`, `--archived`).
- **Wrap-up** — `finish-feature.sh [--repo <name>]... [--into <target>] [--title ...] [--yes] [--merge]` turns the feature branch into one GitHub PR to `<target>` (default `origin/HEAD`'s branch, else `main`). Without flags it checks and prints the plan, then exits 2; refusals (exit 1) list every reason: open tasks based on the feature (`tasks_based_on`), checkout not on a branch / dirty / mid-merge (`checkout_busy`, `checkout_dirty` in `lib.sh`, shared with `start.sh`), feature = target, nothing ahead of `origin/<target>` after `git fetch origin <target>`, `gh` missing or logged out (`gh auth status --hostname`), `origin` not GitHub (raw `remote.origin.url`, `github.com` or `$GH_HOST`; every `gh` call gets `-R HOST/OWNER/REPO`). Warnings (refuse unless `--yes`): merged tasks of this feature with a `review/*.tsk` link still in review, and `git merge-tree --write-tree` conflicts (git ≥ 2.38, else a note). `--yes` = the user's say-so: `git push -u origin <feature>`, reuse `gh pr list --head <feature> --state open` or `gh pr create --body-file`; body = ledger `merged` lines whose sha is in `origin/<target>..<feature>`, abandoned ones whose last commit forked off a feature-only commit under "Not included", ending with the Claude Code attribution line. `--merge` = `gh pr merge --merge` of the open PR (refuses unless the local branch equals `origin/<feature>`), `git fetch`, prints (never runs) the checkout/pull/branch-delete follow-ups. The PR is recorded in `features/<feature, / as -->.pr` (`feature_pr_file`; key=value `feature target url number repo created [merged]`, read with `kv_get`); `status.sh` lists those without `merged=`. `pr-watch.sh <url>` waits on `gh pr checks --watch` and ends with `PR CHECKS PASS|FAIL <feature> <url>`. No board writes. Everything is keyed off one `root`. Workspace mode: `--repo` is required (refused in single mode) and runs it in `<ws>/<repo>` (`feature_branch <repo>`, `tasks_based_on <repo> <feature>`, only `<repo>/` ledger lines, shown without the prefix; record `features/<repo>--<feature>.pr` (`feature_pr_file <feature> <repo>`) with `ws_repo=<repo>`; ledger `- <date> <repo>/<feature> pr #<n> …`). Several `--repo` flags: the script runs itself once per repo, first all as plans (one refusal, or with `--merge` but no `--yes` one warning, refuses all), then for real; with `--yes` it adds a "Part of: <other PR urls>" line to each PR body (`gh pr view`/`gh pr edit`, before the attribution line, replacing an older one) and prints a summary of all URLs. `pr-watch.sh` prints `<repo>/<feature>` from `ws_repo=`; `status.sh`'s "Feature PRs" lines start with `<repo>:`.
- **Memory** — `finish-task.sh` appends one line per closed task to `history.md` (date, slug (workspace mode: `<repo>/<slug>`), merged/abandoned/research, sha (research: `<branch>@<sha>` or `<sha>`), board T-number if linked, the report's `Summary:` line, the brief/report/answer paths (dated or, for older tasks, undated, as `state_file` finds them) relative to the state dir — older lines hold absolute paths, and both must keep working; merged/abandoned lines end with `| base: <base>`, older ones don't, and parsers must take both: `finish-feature.sh` reads fields 3–6 and the text up to the first ` | `); `finish-feature.sh` adds `- <date> <feature> pr #<n> — <title or "merged into <target>"> | pr: <url>` (status word `pr`; its parser skips those); `session-start.sh` puts the last 15 lines in the coordinator's context and names the state dir; `scripts/recall.sh [--board] <word>...` searches the ledger, briefs, reports and research answers (and, with `--board`, the repo's board tasks).
- **Shared helpers** — `scripts/lib.sh` (`set -euo pipefail`, `die`, `state_dir` (path from `state-path.sh`; see workspace mode above), `repo_state_dir`, `state_get`, `repo_root`, `require_coordinator`, `check_slug`, `state_set`; workspace: `ws_mode`, `ws_root`, `ws_repos`, `board_project`, `task_repo`, `task_root`, `repo_default_branch`, `rex_block_alive`; workspace tasks: `ws_check_repo`, `ensure_excluded`, `task_label`; feature: `checkout_branch`, `resolve_feature`, `feature_branch`, `task_base`, `open_task_slugs`, `tasks_based_on`; checkout: `checkout_busy`, `checkout_dirty`; feature PRs: `feature_pr_file <feature> [<repo>]`, `kv_get`; board: `have_tsk`, `tsk_try` (warns, never fails; exit in `$TSK_RC`, exit 3 = indeterminate), `tsk_task`, `thread_name`, `tsk_set_thread`, `tsk_link`, `tsk_link_file`, `one_line`, `canon_dir`; reports on the board: `report_section`, `check_spec`, `report_checks`, `report_questions`, `cap_checks`, `tsk_review`, `tsk_note_once`; `research_reads`; dated state files: `today_stamp`, `dated_match`, `state_file`; Rex layout: `rex_warn`, `rex_block_window`, `rex_window_label`, `rex_restore_tab`, `rex_close_board`, `rex_title_window`; plugin records: `plugin_records_file`, `plugin_local_records`, `plugin_drop_local_record`). `repo_root` is derived from the git common dir so scripts work from inside a worktree too.

## Conventions and invariants

- State lives only in `~/.rex-coordinator/<main checkout folder name>-<first 8 hex of sha256 of its physical path>/` (workspace mode: the workspace folder's name and path, same formula) (`$REX_COORDINATOR_HOME` overrides the base; never in the repo, shared across worktrees): `state`, `history.md`, `briefs/`, `reports/`, `research/`, `tasks/`, `review/`, `messages/`, `features/` (feature PR records). `scripts/state-path.sh` computes it and is sourced by both `lib.sh` and `session-start.sh`, so the two always agree. `state_dir` moves a real `<git-common-dir>/rex-coordinator/` (older versions) there once and leaves a symlink at the old path, so workers briefed with old paths and absolute paths in older history lines keep working; `session-start.sh` stays read-only and reads the old folder until then. `start.sh` adds `.claude/worktrees/` to `.git/info/exclude` rather than `.gitignore`.
- Dated state files: briefs, reports, research answers and messages carry a `YYMMDD-` prefix (local date) so `ls` sorts them by age; `history.md` and the non-markdown files (`tasks/*`, `review/*`, `state`) don't. A task's or topic's date is its creation day, kept in `tasks/<slug>.date` / `tasks/research-<topic>.date`, so brief and report share a prefix; a message gets the day it was sent. Every lookup goes through `state_file brief|report|research <slug>` (`lib.sh`): the dated path when a date is recorded (unless only the undated file exists), else the undated file if it exists, else the newest dated match (the `.date` is gone after `finish-task.sh`). Older undated files are never renamed: ledger lines and running workers' briefs point at them.
- `CLAUDE_ROLE=worker` is the guard that stops workers from coordinating; every entry point checks it.
- Board writes: only the coordinator (its scripts, or commands named in the playbook) changes a board task's status, notes, base or replies. Workers may only `tsk steps <uuid> add|toggle` on their own task, and are expected to: they plan their work as steps before starting and tick them as they go (the brief says so). Every board call is best-effort (`tsk_try`) and skipped without `tsk`; a tsk failure never fails git/Rex work. Always `-p "$root"` (absolute; `board_project`: the workspace folder in workspace mode, where tsk refuses `--base`) on project-scoped calls and address tasks by UUID — a worktree is a different tsk project. Always `started --no-dispatch`. `done` is set only by `finish-task.sh --abandon`. Guard non-idempotent writes (`--append-notes`, `reply`, `steps toggle`) by reading first.
- Never test against the real board: tsk has one global store (`~/.tsk/tsk.json`); run tests through a wrapper that sets `HOME` to a throwaway dir.
